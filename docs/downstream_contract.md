# Downstream contract

Consumers must pin a release ID and manifest hash, then read published artifacts only: `security_master`, `symbol_history`, `company_name_history`, `isin_history`, `issuer_master`, `listing_episodes`, `daily_prices_raw`, `daily_prices_adjusted`, `corporate_actions`, `trading_calendar`, `trading_status`, `trading_status_intervals`, `active_universe_daily`, `liquidity_features`, `research_universe_monthly`, `required_research_security`, `unresolved_observed_trading`, and `terminal_events`.

`required_research_security` is the Phase 2 quality boundary. It contains securities that enter monthly `LIQUID_V1` or monthly Top-750 liquidity scope and carries date range, rank, liquidity, identity, adjustment, instrument, and status evidence. Downstream consumers can use it to identify which securities must stay inside the high-confidence review boundary without scanning every monthly snapshot.

The stable interfaces are `resolve_symbol(symbol, as_of_date)`, `company_name_at(issuer_id, as_of_date)`, `isin_at(security_id, as_of_date)`, `history(security_id, start, end)`, `adjusted_history(security_id, start, end)`, `active_on(as_of_date)`, `profile_on(as_of_date, "LIQUID_V1")`, `eligible_on(as_of_date, ...)`, `ranked_liquid_on(as_of_date, n, metric=...)`, `status_on(as_of_date)`, `observation_status(security_id, as_of_date)`, `sessions_between(start, end)`, `research_quality_on(as_of_date)`, `feature_readiness(as_of_date)`, `candidate_promotion_contract()`, `candidate_promotion_status()`, `candidate_promotion_decision(candidate_start)`, `candidate_promotion_summary()`, `candidate_gate_pass_start_dates()`, `candidate_gate_pass_ready(candidate_start)`, `candidate_research_ready_start_dates()`, `candidate_research_ready(candidate_start)`, `earliest_candidate_gate_pass_date()`, `terminal_recovery_scenarios(security_id)`, and `terminal_event_resolution_queue_for_holdings(security_ids)`. `profile_on()` returns rows with `profile_id`, `profile_version`, `as_of_date`, `eligibility_result`, and `eligibility_reason_codes`. `observation_status()` returns `NO_MARKET_SESSION`, `SECURITY_NOT_LISTED`, `SECURITY_SUSPENDED`, `TRADED`, `NO_TRADE`, or `UNKNOWN`; it does not infer a trade from a missing row. `research_quality_on()` returns release-scoped quality such as `SOURCE_ONLY`, `FEATURE_WARMUP`, `RESEARCH_EXPLORATORY`, or `RESEARCH_HIGH_CONFIDENCE`. `feature_readiness()` reports prior official sessions and configured readiness windows; it does not fabricate pre-source history. `candidate_promotion_contract()` returns the machine-readable candidate start dates, required fields, hard-failure keys, gate keys, allowed values, and pass/fail constants for pre-2013 promotion evidence. `candidate_gate_pass_start_dates()` returns configured candidate starts whose audit status, first-class gates, and promotion interpretation all pass. `candidate_gate_pass_ready(candidate_start)` returns whether one configured candidate start is in that gate-pass set and rejects unconfigured candidate dates. `candidate_research_ready_start_dates()` returns starts that are both gate-pass and `RESEARCH_HIGH_CONFIDENCE`. `candidate_research_ready(candidate_start)` requires both candidate gate-pass evidence and `RESEARCH_HIGH_CONFIDENCE` at that date. `history()` reads nominal raw prices. `adjusted_history()` reads the separate research-adjusted artifact and never rewrites raw history. `DataPlatform.from_release()` reads the published security master, effective-dated company-name and ISIN histories, and queries Parquet prices, universe, liquidity, calendar, and status data. It also exposes `quality_tier`, `verified_start`, and `verified_end`. When `research_release_manifest.json` declares `RESEARCH_HIGH_CONFIDENCE`, strict mode uses that scoped research interval rather than broad raw archive dates. Effective-history lookups fail when zero or multiple rows match the requested date. Calendar results contain only official source-backed sessions; no weekdays are generated. Status queries return `ACTIVE_TRADING`, `SUSPENDED`, `DELISTED`, or `UNKNOWN_STATUS` intervals with evidence quality. Recovery scenarios are labelled `ZERO_RECOVERY`, `LAST_OBSERVED_PRICE`, or `DOCUMENTED_VALUE`; they do not overwrite a null canonical terminal value. The holdings queue API accepts downstream-held `security_id` values and returns terminal-event rows that need focused forensics. Use `DataPlatform.from_release(path, strict=True)` to reject dates outside the scoped verified date range; the default is permissive and returns available rows.

Phase 3 releases expose early-history candidate promotion evidence in `research_release_manifest.json`. Downstream code must treat `candidate_promotion_decisions` and `earliest_candidate_gate_pass_start` as evidence for pre-2013 readiness, not as a substitute for `research_quality_intervals`. Candidate decisions include `candidate_start`, `candidate_audit_status`, `decision_window_gate`, `warmup_gate`, `session_liquidity_gate`, `identity_gate`, `price_action_gate`, `instrument_gate`, `status_gate`, `hard_failures`, and `promotion_interpretation`; the authoritative ordered sets are published as `CANDIDATE_DECISION_REQUIRED_FIELDS` and `CANDIDATE_DECISION_GATE_KEYS`. The authoritative summary field set is published as `CANDIDATE_PROMOTION_SUMMARY_FIELDS`, and the candidate helper method names are published as `CANDIDATE_PROMOTION_API_METHODS`. Allowed audit status values, gate values, and promotion interpretations are published as `CANDIDATE_AUDIT_STATUS_VALUES`, `CANDIDATE_DECISION_GATE_VALUES`, and `CANDIDATE_PROMOTION_INTERPRETATION_VALUES`. Shared primitive candidate values are published as `CANDIDATE_PASS_VALUE`, `CANDIDATE_FAIL_VALUE`, and `CANDIDATE_NOT_RECORDED_VALUE`. Candidate decision rows must match the generated `candidate_promotion_audit_<release>.json` rows for `candidate_audit_status` and `hard_failures`; boolean hard-failure fields must remain booleans, and count fields must remain integers. Manifest layers must provide `candidate_promotion_decisions` and `earliest_candidate_gate_pass_start` together; publishing only one of them is invalid. If candidate evidence is present, it must include every configured start in `CANDIDATE_RESEARCH_START_DATES`, including `2006-01-01`, and downstream API output is normalized to that configured order. `candidate_promotion_summary()` includes `recorded_earliest_candidate_gate_pass_start` from the manifest, derived `earliest_candidate_gate_pass_start` from row-level evidence, `recorded_matches_derived_earliest_candidate_gate_pass_start`, `candidate_gate_pass_start_dates`, and `candidate_research_ready_start_dates`. The gate-pass list is advisory; the research-ready list also requires `RESEARCH_HIGH_CONFIDENCE`. If a candidate audit row is not recorded, the generated candidate decision remains fail-closed with active boolean hard-failure fields. A candidate decision with `CANDIDATE_GATE_PASS_INTERPRETATION` means `candidate_audit_status` is `PASS` and every first-class candidate gate is `PASS`, but full release evidence, including source integrity, PIT invariants, regression, tests, and CI, must still pass before a new `RESEARCH_HIGH_CONFIDENCE` interval can be consumed. If manifest `earliest_candidate_gate_pass_start` is `null`, no pre-2013 candidate is eligible for promotion in that release; if it is set, it must be a configured candidate start and must equal the earliest row with `CANDIDATE_GATE_PASS_INTERPRETATION`.
